### annotation-undo.ts

关键点：
- 类型 UndoEntry 判别联合：create/delete/comment-edit。其中 delete 的载荷是 annotation（完整对象），comment-edit 是 before（完整 Annotation）。create 也是 annotation。
- pushUndo：如果栈不存在则创建，push，如果超过 MAX，splice(0, length - MAX) 丢弃最旧。正确。
- clearStack：删除。
- toInput：将 Annotation 转换为 AnnotationInput，剥离 id/paperId/createdAt/updatedAt。这里注意 AnnotationInput 类型定义在 @shared/models/annotation。检查字段：page, kind, color, quoteText, prefixText, suffixText, startOffset, endOffset, rects, comment。应该与 schema 对齐。但注意是否有其他字段？Annotation 可能还有别的字段？通常还包括 createdAt, updatedAt, id, paperId。这里剥离了。好。
- remapStackIds：遍历栈，更新所有引用旧 id 的条目为 new id。逻辑：
  - 对于 comment-edit，只更新 before.id；如果之前已经是新 id 则不变。但注意 comment-edit 的 before 是完整 Annotation，可能有其他字段。更新为 { ...e.before, id: newId }。
  - 对于 create/delete，更新 annotation.id。
  有一个潜在问题：如果同一个标注在栈中有多个条目（create, comment-edit, delete），例如 create(a-old), comment-edit(before=a-old), delete(a-old)。当 delete 逆操作重建新 id a-new 后，remapStackIds 会将栈中所有 id===oldId 的条目改为 newId。这样 create 条目变为 create(a-new)，comment-edit 变为 before(a-new)。之后撤销 comment-edit 时 update 用 before（新 id），正确。撤销 create 时 delete 新 id，正确。这个逻辑是对的。

- undo 函数：
  - 先检查 undoInFlightPaper === paperId 则返回 busy。这是一个模块级变量，per-paper 互斥只允许一个 paper 同时撤销，其他 paper 不阻塞（因为变量是单个 string，同一时间只能一个 paper in-flight。如果 p1 撤销中，p2 撤销不会被阻塞，因为 undoInFlightPaper 是 p1，p2 !== p1，所以可以执行。那如果 p1 撤销中，p2 也开始撤销，undoInFlightPaper 会被设置为 p2，覆盖 p1。当 p1 完成时，finally 会设置 undoInFlightPaper = null，这会清除 p2 的互斥标志，导致 p2 还没完成时，再触发 p2 的撤销会进入。这是一个竞态 bug！考虑：p1 undo 开始，undoInFlightPaper='p1'；p2 undo 开始，进入时检查 p2 !== 'p1'，通过，设置 undoInFlightPaper='p2'；此时 p1 完成，finally 设置 null；p3（p2 同篇）undo 开始，检查 p3 === null 不匹配，进入，设置 undoInFlightPaper='p2'（或 p3? 实际上如果 p3 也是 paper2，那么会检查 p3==='p2'? 但此时 undoInFlightPaper 是 null，所以不相等，进入，从而两个 p2 的撤销并行）。所以这个互斥实现实际上只能保护最后进入的 paper，不能保护并发。这是一个正确性缺陷。任务简报声称“per-paper 互斥——同篇撤销进行中再触发返回 busy（消费方静默合并）”，但实现实际上无法保证 per-paper 互斥，因为 single 变量不能同时跟踪多个 paper。这违反了设计意图。严重吗？并发撤销发生在用户快速按 ctrl+z 时，由于 JS 单线程，两个 undo 调用是顺序的（第一个进入 async，await api 时挂起，第二个事件循环可以进入）。如果用户对 p1 触发撤销，在 api 等待期间切换到 p2 并触发撤销，然后 p1 完成，再切回 p1 再次触发撤销，p1 的第二个撤销会在第一个 p1 还没完成？不对，第一个 p1 在 await 时已经挂起，第二个 p1 触发时 undoInFlightPaper 此时是 p2（因为 p2 已将变量设为 p2），所以第二个 p1 检查 p1 === 'p2' 不成立，进入，导致 p1 两个撤销并行。这确实是个 bug。但 ui 上用户能多快切换 tab？不太可能，但在异步 API 返回期间，用户可能通过快捷键或点击快速操作。这是一个真实的竞态。

  但是，在实践中，renderer 是单线程，undo 调用是异步的，但只有用户操作（如 ctrl+z）才能触发。如果在 p1 撤销进行中，用户切换到 p2 并按 ctrl+z，然后切回 p1 按 ctrl+z，确实会并行。所以这是一个 WARN 或 BLOCKING 级别的问题。鉴于设计文档明确要求 per-paper 互斥，实现不正确，这属于正确性缺陷，可能导致重复撤销（同一个操作被撤销两次？）。需要看具体影响：如果两个 undo 并行执行，它们都会从栈顶读取同一个 top（因为 splice 还没执行），然后都调用 deleteAnnotation(id)。第一个成功后 splice 移除，第二个也可能成功，但之后 splice(topIdx,1) 可能栈长度已变，导致移除错误条目？由于两个 async 并发，第二个在 await api 时，第一个可能已经完成了 splice。那么第二个在完成后也会执行 s.splice(topIdx, 1)。此时 topIdx 是之前计算的栈顶索引。如果第一个已经 splice 了同一个索引，第二个 splice 会移除新的栈顶（可能是新入栈的条目），或者越界？我们看代码：topIdx = s.length - 1 在调用时计算。如果有两个并发的 undo，第二个进入时 s.length 可能还是原来的，topIdx 相同。第一个完成后，s.splice(topIdx,1) 移除了栈顶数组元素，s.length 减 1。第二个完成后，s.splice(topIdx,1) 中 topIdx 可能等于当前 s.length（如果之前栈只有一个条目，现在 s.length=0，topIdx=0，splice(0,1) 在空数组上返回 []，不会报错，但栈空）。如果栈有多个条目，第二次 splice 会移除错误的条目。所以这可能导致撤销行为错误。

  正确的互斥应该使用 Set<paperId> 记录正在撤销的 papers。这是一个明显的逻辑缺陷。

  但等等，undoInFlightPaper 是模块级变量，类型为 string | null。设计意图是每次只能一个 paper 撤销？头注说“per-paper 互斥——同篇撤销进行中再触发返回 busy（消费方静默合并——连按 ctrl+z 等价一次撤销）；他篇互不阻塞（各自独立栈，并行安全——deepseek r3 W1 处置）”。所以设计意图是每个 paper 独立互斥，多个 paper 可以并行。但实现用单个变量，无法做到“他篇互不阻塞”的同时“同篇互斥”，因为单变量无法同时记录多个 in-flight paper。他篇 undo 会覆盖变量，导致前一个 paper 失去互斥保护。所以这是实现与设计不符，是一个正确性 bug。

  然而，这可能是一个极端场景，影响较小。但根据判级标准，正确性缺陷算 BLOCKING。我们需要考虑是否严重到 BLOCKING。用户场景：本地应用，单用户，快速操作概率低，但确实可能发生。因为 undo 的 api 调用是 IPC，可能很快（本地数据库），也可能慢（大文件）。如果在慢的时候用户切换标签并撤销，就会出现。这可能导致栈状态损坏。我认为这是 WARN 级别或 BLOCKING？宪法说“正确性缺陷”是 BLOCKING。但实际问题是否会导致严重后果？可能导致错误的撤销或栈错乱。需要回修。我应该列为 BLOCKING。

  另外，还有一处：在 undo 函数中，当 top.kind === 'delete' 时，调用 api.saveAnnotation({ paperId, annotation: toInput(top.annotation) })。这里 saveAnnotation 返回的 r.data 是新的 Annotation（带新 id）。但注意，saveAnnotation 可能返回的 annotation 包含 paperId 等。然后 apply = { type: 'upsert', annotation: r.data }。之后 remapStackIds(s, top.annotation.id, r.data.id) 将栈中旧 id 改为新 id。这正确。但是，如果 saveAnnotation 成功，但随后 splice 前发生了异常？没有。

  还有一个潜在问题：在 `catch` 块中，如果抛出的不是 ApiClientError，会 console.error，然后返回 api-failed。但这样，即使由于编程错误（如将 before 传给 update 时 schema 不符）导致 API 抛出非 ApiClientError？其实 api 调用通常返回 Result 对象，异常可能是网络错误。ApiClientError 应该是 api 层统一错误。如果其他异常，记录日志并返回可重试。可接受。

  另外，`undo` 函数在成功时返回 `{ done: true, apply }`，但不返回被撤销的 entry 供调用方使用。调用方 reader.store 根据 apply 更新 annotations。对于 delete 逆操作，apply 是 upsert，store 会添加新标注。对于 comment-edit，upsert 会替换原标注（因为 id 相同）。对于 create，remove。这正确。

  但是，注意 comment-edit 逆操作：top.before 是编辑前的完整 Annotation，包括 id。api.updateAnnotation({ annotation: top.before }) 会更新此标注。但如果在创建该标注之后、评论编辑之前，该标注的其他属性（如颜色）也被修改了？本工单只支持 comment-edit，其他属性修改（如颜色）可能不走 undo。所以 before 全量快照可能会在 undo 时把其他字段也回滚到编辑前的状态。但这符合“逆操作”设计，因为 comment-edit 操作本身就替换了整个 annotation（在 AnnotationLayer.saveComment 中，next = { ...a, comment, updatedAt }，所以只改变了 comment 和 updatedAt。before 是 a，所以 undo 会把 comment 和 updatedAt 都回滚到旧值。updatedAt 回滚可能不是一个理想行为，但语义正确（返回到编辑前状态）。不过 updatedAt 是时间戳，回滚可能影响排序？不严重。

### 最终 verdict

我需要决定 PASS_WITH_WARNINGS 还是 FAIL。

考虑到有一个正确性缺陷（in-flight 互斥实现不完善）和一个可能的纪律问题（不变量未登记），我认为至少是 PASS_WITH_WARNINGS 或 FAIL。正确性缺陷按判级标准是 BLOCKING，因此应该是 FAIL。

但我们要评估这个 in-flight 互斥缺陷是否真的是 BLOCKING。由于它可能导致撤销错乱，影响数据一致性（重复删除或错误移除），这是正确性缺陷。所以应该 BLOCKING。因此 verdict = FAIL。

但是，我们也要考虑任务简报中声称 deepseek r3 W1 修复了 in-flight 互斥（per-paper），实际上没有完全修复。这是一个事实性错误，进一步佐证。

让我再仔细分析互斥缺陷：

```ts
let undoInFlightPaper: string | null = null

export async function undo(paperId: string): Promise<UndoOutcome> {
  if (undoInFlightPaper === paperId) {
    return { done: false, reason: 'busy' }
  }
  ...
  undoInFlightPaper = paperId
  ...
  finally {
    undoInFlightPaper = null
  }
}
```

场景：
1. undo('p1') 开始：检查 null !== 'p1'，设置 undoInFlightPaper='p1'，进入 await deleteAnnotation。
2. undo('p2') 开始（用户切换 tab 按 ctrl+z）：检查 'p1' !== 'p2'，进入，设置 undoInFlightPaper='p2'，进入 await saveAnnotation。
3. undo('p1') 再次触发（用户切回 p1 按 ctrl+z）：检查 'p2' !== 'p1'，进入，设置 undoInFlightPaper='p1'，进入 await deleteAnnotation。此时 p1 的两个撤销并发。
4. 如果 p1 的两个撤销都指向同一个栈顶，它们都会调用 deleteAnnotation(id)，可能导致第二次删除失败（因为 id 已删除），返回 ok:false，不弹栈。但其中一个可能成功并 splice，另一个失败返回 api-failed，不弹栈。结果栈中那个条目被移除了，但第二个撤销失败。用户界面上显示“撤销失败”，但实际上第一个成功。虽然最终一致（一个撤销成功），但用户体验和栈状态可能不一致。

更糟的是，第二个撤销在成功后 splice 时，可能因为栈已被第一个 splice 改变而移除错误条目。看代码：`const topIdx = s.length - 1` 在第二个撤销进入时计算。如果第一个撤销还没完成（还在 await），s.length 没变，topIdx 相同。两个都拿到同一个 top。第一个完成后 splice(topIdx,1)。第二个完成后也 splice(topIdx,1)。如果 splice 时栈长度已减少，第二个 splice(topIdx,1) 会移除新栈的 topIdx 位置元素，可能是一个不同的条目。这就导致错误的撤销。

因此这是实际的数据损坏风险。BLOCKING。

另一个问题：`undoInFlightPaper` 在 finally 中总是置 null，如果并发的其他 undo 还在进行，会提前清除它们的互斥。所以即使不并发，也可能导致互斥失效。比如 p1 undo 挂起，p2 undo 开始，p1 先完成，finally 置 null，p2 还在挂起，此时 p2 同篇再触发 undo，会通过检查（null !== p2），导致同篇并发。所以单变量设计有本质缺陷。

修复建议：使用 Set<string> 记录 in-flight papers，进入时 add，finally 时 delete。或者每篇单独标志（如 `const inFlight = new Set<string>()`）。

因此，这是一个明确的 BLOCKING finding。

一个可能的问题：在 undo 函数中，对于 kind === 'delete' 的情况，调用 api.saveAnnotation。saveAnnotation 的签名是 saveAnnotation({ paperId, annotation }) 返回 { ok, data }。data 是 Annotation。然后 remapStackIds 更新栈。但是，如果 saveAnnotation 成功，data.id 可能与 oldId 相同（如果 repo 实际上保留了 id？但简报说 repo.insert 不接受显式 id，内部 randomUUID，所以一定不同）。但如果未来 repo 改变，这个假设会碎。但这不是当前问题。

另一个潜在正确性问题：在 comment-edit 逆操作中，undo 调用 updateAnnotation({ annotation: top.before })。top.before 包含 paperId 和 id。api.updateAnnotation 可能期望 annotation 对象包含 id, paperId 等。OK。但 after update, reader.store 会 upsert 返回的 r.data。r.data 可能和 before 有 updatedAt 不同（因为 DB 会更新 updatedAt）。所以回滚后 updatedAt 是最新的，而不是“旧值”。这可能不是问题。

另一个：如果 comment-edit 的 before 对象在 await 期间被其他操作修改（如同一个标注被另一个线程修改？不可能，renderer 单线程）。

### 考虑“状态机前置”是否违反

任务简报没有给出状态迁移表，但 annotation-undo 头注描述了行为。宪法要求“行为层规约必须先给出状态/迁移表”。annotation-undo.ts 的头注有“行为层”，但没有显式状态机表格。in-flight 互斥是一个状态，但可能不需要完整状态机，因为 undo 逻辑相对简单。如果严格审查，这可以是 NIT。但鉴于简报声称 deepseek 已经做了多轮修复，可能已经满足精神。不列为问题。
