**第 0 节 - 两个测量系统中投影的一致性**

设计断言：
- 持久化坐标系 = page-normalized fraction（anchor.rects）
- 两套测量系统向该坐标系投影同一文本
- PDF 声明几何 = 防御失真——根植于文档自身坐标系
- 浏览器渲染测量 = 在病理性页面上失真
- 数值关系（依据 §3-2 selectionHealth evidence）：健康页面偏差 0~0.12% → seam 风险潜伏无法观测；病理性页面差异 25~62.5% → 基于 DOM 的投影是错误的

设计声称在健康的页面上，A/B 行为是等价的，方案的差异只在病理性页面才会显现——而彼时的可信投影是 item geometry family。这就为 A. 优于 B. 提供了核心论据。

这里存在潜在漏洞：
1. 声称“在健康的页面上，A/B 行为是等价的”——这是真的吗？A 方案（item geometry chain）和 B 方案（guard + coexistence）在健康页面上的行为是否完全等同？实际上并非如此。即使在健康页面上，item geometry projection 与 DOM geometry projection 也可能存在微妙差别（item geometry 可能无法捕捉某些 CSS 布局特性，如 line-height 差异、额外的 letter 间距等）。如果 DOM 测量能够捕捉到 item geometry 遗漏的一些视觉细节（例如 CSS 变换、字体回退、文本渲染差异），那么在健康页面上它们可能并不等同，但即便存在细微差异，由于偏差在 0%-0.12% 之间，这些差异或许不会造成视觉可见的问题。
2. “健康页面 IoU≈1 但并非完全=1”——该陈述表明项目内部数据，但偏移差异虽小却真实存在。这是否是替代方案选择的部分标准？

实际上更深层的潜在漏洞在于：设计明确同意 B 在病理性页面上无法生成正确的值（只能检测并降级）。但 B 的主要价值，是将 DOM 测量作为一种“双重检查”或验证手段，而不仅仅是另一个几何来源？抑或 B 的本质在于治理两套测量系统的共存——通过守卫来保证不会错误配对？设计以此论证：B 在病理性页面上只能“检测并降级”——而这在设计作者看来使得 A 成为更优选择。

但还有一件可能被遗漏的关键事项——这或许是一个重大的审查发现：**selection-evaluate.ts header 中体现了“三层回退”与 item-geometry 优先的做法**（快路径 → full path → DOM measurement）。设计提到了 F-A6 的三层回退，但正确指出现有注释标注的层级：快路径（ITEM DOMAIN）→ 全量（用于 mouseup 路径，其本身具有 DOM measurement fallback）→ DOM measurement。

嗯，可验证的是，selection 路径的锚定（settle/mouseup 全量路径）原本就具有 DOM 测量回退构建。而设计使注释链路保持三种时态并存——但这并非确切关切。

**与简报的一致性：状态空间 S0-S6**

设计定义了这些状态：
- S0 mount：读取 page-items.store（§3-3 direct-read precedents）
- S1 item reconciliation：如果 store 命中，则运行 reconcileItemsWithDom → false 则 S4
- S2 citation reconciliation + re-anchor 中：verifyQuoteItem 校正 → rectsForOffsetRange + bandsFromItems → 如果成功 S3a 否则 S3b
- S3a resolved（item geometry domain）
- S3b single-item fallback to stored values——存储的 rects + bandsNearRects
- S4 page-level fallback（DOM measurement）——当 page items 缺失/reconciliation 失败时；DOM chain 整体降级为回退层 → G2 健康时转 S5，G2 病理性时转 S6
- S5 resolved（DOM domain，标记）——仅用于展示

对于“S4 → G2 健康 → S5”或“S4 → G2 病理性 → S6”这个流程，一个值得怀疑的点是：**G2 检查使用 selectionHealth 来判定页面级采样是否病理性，但 selectionHealth 是为 selection 域设计的检测器（在 selection 路径中）。若其输入是对齐的选段产物，而非带注释的锚链……将 selectionHealth 作为特定页面的通用“病理性页面”评价指标，再用于重锚链路，是否恰当？** 设计说（第 1.1 节）：“G2 判定依据 §1 selection-evaluate 先例「unhealthy→抑制」。S6 为新增格，理由：病理页 DOM 回退产物即 R2 之害本身。” 然而，selection-evaluate.ts 提及 selectionHealth 用于鼠标悬停路径——它评估的是基于 DOM 文本层状态的 selection 健康状态。但 page annotation 的 anchor 链路先以何种方式修改 DOM？请细想一下 selection 是文本层的简洁片段，DOM 量测时能更接近于测量文本层——如果整个文本层因 pdf.js 过程而出错，影响的是所有依赖该文本层 DOM 的量测操作。在 measure page 的 select 场景与 measure page 中的 annotation anchor 场景中，在同一个文本层 DOM 上是否会观察到类似的失效模式？如果依据 V1/F-A6 evidence，text-layer 异常形态会导致 25–62.5% 的偏离，那么是的，两者都会受到影响。不过，selectionHealth 在 selection-evaluate.ts 中的既定用途，是用作拖选期的抑制开关；此处却将其重新用作一个通用页面级病理性指标——这很可能可以呈现成一处需要做出说明的假设。

**针对 §0 逻辑的批判性评价**：
§0 说：健康页面上 A/B 行为是等价的；它们只在病理性页面上存在差异——彼时的可信投影即 item geometry family。这引出 A 优先于 B.

论点缺陷如下：
1. “等价”并非完全正确的比对——在健康页面上，A 会生成 item geometry 投影；B 会守卫 DOM measurement projection 并保持向后兼容。交付物不同（一种作为 future-proof 的投影，另一种是基于 DEM 的兼容实现），但用户所见的视觉输出非常接近。将 A 与 B 在“行为等价”幌子下等量齐观，混淆了正确度与视觉外观。
2. 即便在健康的页面上，item geometry vs DOM 测量之间也存在差异——只是小的系统性偏置/非偏差性差异。若要声称某种“完全等价”，有些草率。
3. 即使病理性页面确实从 DOM 投影中引出了失败，A 也无法覆盖 item store 重建中存储条目的场景；B 相反聚焦于守卫但无法正确重建——但是，当一个 item store 中同时存在 items-based 和 DOM-based 的存量时，设计到底如何解决读取和合并这些异构的现实？如果 A 是 winner，它仍需要处理一个现实：库值是在 DOM measurement 域中存储的。“resolution”可能不是归一的（或者是？）

实际上，我需要仔细注意 **R3**：verifyQuote 校正 —— 设计承认 A 不能满足：“该项自愈”需要使用 item geometry 来构建等价物。第 3 节设计 verifyQuoteItem(items，startOffset，endOffset，quoteText，prefix?，suffix?)——声称使用全部来自材料库的模块组件构建该 object 是可能达到的。该对象首先通过 buildItemOffsets(items) 构建 span{...} 数组，然后粘合得到文本，采用与 selectionToAnchor 相同的 quote/prefix/suffix 切片逻辑来查找 quoteText——这依赖：①selectionToAnchor 的切片逻辑必须与可声明断言一致；②材料中锚中是否真的记录过该切片逻辑吗？

所以，设计大致承认此前的叙述尚未被验证。它确实标注为需主控验证条目，但这并不完全可靠——由于 A 在病理页面处理中会破坏 verifyQuote 语义，因此这种域内等价物成为硬要求。若非纯文本可复用，则若要完成 verifyQuote（设计声称可重用的同名区块）需要编写新的逻辑——新的逻辑若出现缺陷，不会影响现有自愈，而是会影响 item-based equivalent 的基石。

**设计文档更缺乏的一个关键是：它并未考虑何时需要重锚，及锚链是否真的需要再次运行 verifyQuote。**

所谓“verify”，是对比已存储的 anchor quote text 与渲染生成的 DOM 文本（即文本层 DOM）——如果人工在选中文本内容时其对应 pdf 文本与 DOM 因字号/样式投影存在系统性位移（排版偏移），所存储的 offset startOffset/endOffset 需经过校正。但如果 DOM 与 item store 在文本上是一致的，是否可以简化 verify？该 design 在 Section 2 进一步说明 verifyQuoteItem 与 verifyQuote 的域语义是等价的。

我在此标注：因为当前 annotation anchor 保存域（F-A6 domain of selection）的注释锚、recalls 是否也在消费 pdf-item-geometry，这确实是一个确切的原始域（F-A6 域=selection 产链），所以 item store 是被自身实现使用的。

让我们聚焦于设计中的真实缺陷：

**缺陷1状态空间：状态 S0 直接读取 page-items.store —— 但没有任何异步语义或取消机制。当前链路由 rAF (requestAnimationFrame) 调度，读取 DOM 量测作为同步值。当标注正在显示/正在修改，而 store 中没有任何 items，或 store 尚在加载中时——S0 是持续了 rAF，还是等待 store——在 render 链路读取时立即失败？**

该 design 称 S0 直接读取 page-items.store（§3-3 direct-read precedent——快路径的 precedent in selection）。但 selection 测量针对一个正被用户选中的文本（有一个确定性锚的上下文），annotation 可能在其显示寿命中随时出现。若 store 为空/缺席，S0 将过渡至 S4 回退——但 store 何时就绪？这是否会使注释先闪现 DOM 回退态，而后当下一个 mutation 到来时跳到 item geometry 态？

设计文档表示变异监视器（MutationObserver）与现有节奏保持，但若 item store 尚未变更—— item 进入后是否会触发？来自 task brief 的 page-items.store 项：store 被“注册 item/page geometry...”。其中是否存在一个 observer 订阅可以令 annotation layer 在页面 item 注册时察觉出现？task brief 未详细说明加载语义，仅指出 store 是 zustand。因此，“store readiness race”是否被材料覆盖的事实尚不明确。若这一前置性组件缺失，实际落地很容易出现条件竞争——标注会在 loads 中按照 DOM-measurement 显示，然后切换到 item geometry，这违背了解决方案“正确投影”的目标。

但这也许是一点瑕疵——实际上调用 MutationObserver 的工作方式是：文本层的文本覆盖在每次解析时完成；这就立刻 refresh 值。如果已注册 page items store，那么只要文本层中的 spans 渲染，resolve 就会运行；如果 annotation layer 先运行于覆盖渲染之前，就走 DOM 值；之后当 DOM 文本渲染并触发 mutation，resolve 会再次尝试 item store ——如果 store 未加载，就会返回 DOM-measurement——当 store 载荷加载完成时，没有任何 mutation 会在 DOM 中触发，因此基于 item 的解析永远也不会进行。只有 store 中某 listener 存在时才会触发 re-resolution。这一点缺乏处理。

然而，在 selection 世界中 store 发生于 selection 事件，DOM 文本层已经就绪。在 annotation 场景中，其运行时序彼此独立，因此必须协调 store 供应与文本层解析。设计并没有说文本层解析和 item store 数据注册都已完成，并整合于统一流程的判断中。它在第6节 S4 项中提及：fallback=“store 就绪后 MutationObserver 节奏重入 S0”。 但 store 状态变更方式并不引发 mutation observer。MutationObserver 观察的是 textLayer DOM，而不是 store。如果 store 延迟 arrive，而文本层不再改变，则不会触发任何重试。且 store 就绪项（第7节,page-item 缺席）这一条为风险是否足够？

**缺陷2：混域现状跨 store resets 的表现** —— 如果 anchor.rects 既有 item 又有 DOM 域，而 item-based chain 在 render 时通过混序归并（） / 现有值并串？render 路径的做法是 resolved ? resolved(a.id)?.rects??a.rects、resolved ? resolved(a.id)?.bands : fallbackBands。如果 anchor.rects item-based 存在，匹配了 resolved item 值，实际得到相同的值——matchBand selected band 恒等于该 rect 相同族来自 band coverage 原本存于 rects 内的几何。但若是 legacy DOM location matching failed，就落到 a.rects —若 a.resolved 存在即采用 item，若是 item 不存在就从遗留数据取——即 item→ 若你 item。

然后重要部分：那 fallback 当 DOM/resolved?===不存在时老 rects 从 legacy DOM 展示经 S3b fallback state? 状态 S3b：single-item fallback——存储的 rects + bandsNearRects。但 bandsNearRects 需要 textLayer DOM 测量（其实是 DOM），rendering history 说 fallbackBands 在全局文件中按失败集生成。尚未崩溃？

其实注释说明：bandsNearRects(textLayer, rects) 是 DOM 测量。设计让一条 S3b 时继续使用 bandsNearRects，但此前，在 S3b 的每个分支里，“若 rect 来自 legacy DOM 域而与 render 匹配—— 它可理解为 rect 配对于遗留 bands 的同家”—— 但若 rect 在 item 域、bands 经 DOM，问题即 R1 经此返回（设计本身称 S3b is 中的可跨越的家族配对，依 INV-59 作限定）。这无法解决触发它的 R1，所谓 single-item fallback “采用 old rects+bandsNearRects”构建状态 —— fallback 到底意味着什么？

对此设计在 S3b 说：“该引文 quote reconciliation 失败则 →将存储 rects 与 bandsNearRects 作为各自保留值的 fallback……现有语义保持逐位一致（不劣化现状）”。但这会产生原封不动的 R1。设计承认这一情况存在于 S3b，并以 INV-59 将其备案—— “跨族配对仅允许在 S3b/S5 fallback 单元格中并作为已知边界登记”。将 uneliminated R1 视为已识别限制，是否是放弃得过多？

不过，如果用户现有工作流本已包含 DOM fallback，这与当前的故障模式一致，因此不会变差。但这并未消除 R1——只将主链中的消除，把剩余部分引入 S3b+登记。设计列下“R1 residual（S3b/S5 跨族配对）→ INV-59 限制 fallback 单元格并登记 ”。其使用 INV-59 的处理“所有引文都从单一几何域对 account.匹配”，对 R1 残余而言未必是净化。
