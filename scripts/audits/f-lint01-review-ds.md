## 四、漏掉的形态/方案（增量攻击面）

设计书覆盖了 5 类形态，但显然还漏了以下常见对抗源：

### 1. **CSS-in-JS 非 inline `style`（styled-components / emotion / stitches 等）**
设计书 B-5 只覆盖 `JSXAttribute style`，但现代化前端（React 领域）定义 `styled.div` 的方式可无限复杂。当样式引用 `var(--foo)` 时，C-4 的全部推断（只查 `#hex/rgb/hsl`）将放走大量直写在模板字符串的背景色（如 `background: 'red'`, `/linear-gradient` 中的 `red`）。要覆盖它必须走 B 侧的“字面量表达式解析”去识别 `styled` API 的 tag。若不宣布为 Explicit Out-of-Scope，它就是渗透洞。（须在 INV-11 状态注记加入。）

### 2. **缺失的完整性哨兵——“被禁止的旧锚定文件还在不在？”**
设计书只对“新增 CSS”给予负锚检测，但没有检查**负锚数组“七件”**本身是否被人为从重构中删除一个文件，而测试却还被保留着。本质上需要类似“期待文件数量的 manifest 指纹”（比如: `tests/theme.test.ts` 中的锚点数必须与某个预期数相等，否则 fail——正好可以用 C-8 的动态提取文件内部数来检查一个“不少于 7 件”最小断言）。

### 3. **通用数值的双源结构（字体大小, z-index, 动画 duration, spacing）——不只是颜色/字号**
设计书只覆盖 “颜色” 和“超长文字”这两种点。但 F-CSS-02 违规中最常见的其实是 **spacing/ratio**（如 `56px`,`16px`, `0.8s` / `2px` 等 token 复用被硬编码）。C-8 只规定了“新增 CSS 未在 FS_DECL 上下文跑”，它跑的是五通道规则本身，假如五通道 **本身没有枚举这些 spacing 的目标值**, C-8 不会报出“在新文件中写 16px 等同值”。需扩展通道,否则 W1 只防“文件遗漏”,不防“规则遗漏”。

### 4. **“设计变量覆盖强制穿透”——针对 CSS 用了 `!important` 或 overlay tokens 覆盖既有锚点**
设计书只检测“新增的文件”，无从检测在一个旧 CSS 文件的追加区域看到 `color: #fff`（虽然该文件被五通道检查——但需要挑出“非 token 文件名定义的其他全局 :root 后缀优先赋值”等 token 兜底场景）。建议在 CSS 侧增加 [media(query) 下重定义变量需申报] 的规则，否则用户永久性用 `!important` 破坏单一真相源,不会触发已检文件的任何通道——这个没走向 fail。

### 5. **不可见的静默失败状态 (silent-pass on empty extraction)**
已在 C-8 / C-4 中被要求硬错误：任何 token 文件不存在 / 枚举文件为空 / 提取 0 命中时，当前 lint/quality 段将直接通过——这会把所有预期检测置为透明;若不做核心硬校验，该 lint 无意义。设计书原文 C-4 中完全没有“零结果即失败”的描述，极容易被部署成一个永远绿灯的空包。

### 6. **本地 rule 的缓存与并发分组**
B 组规则的跨文件对比，要求 lint worker 并发下共享跨文件 state（eslint 常规状况下各文件 lint 是进程隔离的），如果同一个值比对在单文件独立执行时只能列“单处”，则 B-1 不可能在任何仓库内使用。该实现需在 rule 注册一个 “build cache in a root file” 或用第三参数共享上下文；这种建议需要作为一个实现设计目标。 

以上为增量攻击面——若只在“lint(C) 对已有锚内循环”做无脑扫描，而不解决 token 伪名覆盖与“空集即绿灯”状态，设计书会在真实赛场上退化成形式主义。
