# 组织设计咨询意见（门一/被路由岗位视角）

## 一、四问逐项表态

**Q1 跨项目通用：同意，但附条件。**
组织层与项目侧解耦是成立的，但「通用」的边界必须划在**角色拓扑与协议**上，模型×供应商事实必须完全留在 org-config，否则首个项目（Synapse）的供应商细节会反向渗回技能正文。建议：先以 Synapse 跑一个完整 LOOP 再冻结 v1.0，防过早抽象。

**Q2 三层混合：同意。**
纯文档无法承载派发器这一可执行依赖，纯技能带脚本则丢失宪法层的常加载约束力。但补一条：技能包内含可执行脚本=软件分发件，必须带**版本号+校验摘要**，并在 model-routing-log 中记录派发器版本，否则跨项目会出现「同一技能名、不同派发器行为」的隐性分叉。

**Q3 PM 并入主控：同意。**
独立 PM 岗多一跳模型转述，需求失真风险确实大于分工收益——且 PM 的 intake/立案/排程本质是结构化文书工作，主控以**角色卡/子模式**（而非独立模型岗）承载即可，既保留职能分界面又不增加转述链路。这也与「用户只对接一岗」的原始需求自洽。

**Q4 升级替代：同意，但要求迁移期保护。**
双源漂移是已验证的真实风险（本咨询件暴露的 SYS_PROMPT 硬编码即是一例「事实散落多处」）。建议：①旧技能不立即删除，改置**只读重定向页**（指向新技能+归档说明）保留一个项目周期；②退役前对旧技能做版本归档快照，保证可回滚；③迁移清单显式列出旧技能中哪些内容并入、哪些废弃，避免静默丢失。

## 二、补充风险与改进点（按重要性排序）

1. **派发器角色参数化（新发现的处置）**：建议不要简单把 SYS_PROMPT 改成入参字符串，而是建立**角色档案注册表**（角色 ID→系统提示+审计包模板+DoD 细则），派发器按角色 ID 查表装载。角色即数据而非代码，新增岗位不动派发器本体，locked-change 面最小化。参数化改造完成后**先回归门一现有链路**再启用拟定者岗复用。
2. **路由不可强制的诚实记账机制**：会话内子代理定档是环境限制而非提示词可解，组织技能必须把「环境限制统一档」欠账写成**强制输出项**（记入账本而非口头声明），防止未来维护者误以为路由已生效。这是防静默失败的关键一条。
3. **宪法层厚度无量化防线**：「20~30 行」是愿望不是约束。建议给常加载层设**硬性 token 预算并在技能自检中校验**，超限即拒绝加载或告警，防上下文预算缓慢失守（这类退化无报错、最难察觉）。
4. **org-config 与账本版本对齐**：成本账本按模型×供应商×套餐分列之外，应同时记录 org-config 版本哈希，否则换套餐/换端点后历史成本数据失去可比性。
5. **跨项目首适配场的回灌机制**：Synapse 适配中暴露的端口差异（环境约束、派发器可用性）应有明确通道回写技能移植指南，否则「可移植」只停留在纸面。

## 三、一线体验反馈（被路由岗位视角）

1. **自包含审计包是生命线**：本咨询件能做到零仓库接触且自包含，是可回答的前提。组织技能化后**绝不可丢失「门一零仓库接触=只喂自包含 diff 包」的包内容强制**——这是靠协议而非角色自觉的部门墙，是我最不希望被「灵活化」掉的一条。
2. **审计包尺寸须有界**：过大的 diff 包会挤压分析深度（上下文被证据占满，推理空间萎缩）。建议技能正文写入包尺寸上限与超限拆分规则，而非依赖派发方自觉。
3. **换源对工作连续性影响可控、对质量的影响真实存在**：任务书与 DoD 不随换源放宽，使主源→备源→兜底的切换对任务定义零扰动，连续性良好；但不同模型的审查风格与盲区确实不同，**「记 switch」流水账**是事后归因质量差异的唯一依据，必须保留。
4. **欠账回退机制不可丢**：「全源尽→只读审记欠账」是诚实的降级路径，比假装完成审查好得多。组织技能化后这是我最看重的失败可见性设计。
5. **异构对抗结构不可丢**：门一与实现者异构、门二与实现者异构优先——同模型自审的盲区已被实战验证。这条应写进宪法组织段而非留在技能细节里，因为它定义了「公司」存在的理由。

## 四、一句话总立场

**方案成立、四问全部同意主控推荐，批准上线的前置条件仅两条：派发器角色档案化改造先回归门一链路、旧技能退役走「重定向页+归档快照」的受控迁移——其余按三层形态推进。**
