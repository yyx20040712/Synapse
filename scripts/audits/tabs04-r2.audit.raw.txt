B. main-window.ts 中的 `handleCloseWithQuitGuard`：
```ts
export async function handleCloseWithQuitGuard(
  dirty: boolean,
  event: { preventDefault(): void },
  win: { destroy(): void },
  deps: QuitGuardDeps
): Promise<void> {
  if (!quitDirtyGuard(dirty)) return
  event.preventDefault()
  let confirmed = false
  try {
    confirmed = await deps.confirmQuit(QUIT_CONFIRM_MESSAGE)
  } catch {
    confirmed = false
  }
  if (confirmed) win.destroy()
}
```

- 如果 dirty，preventDefault 同步调用，然后 await 确认框。OK。
- 异常按取消处理，窗口保持。OK。
- 确认后 `win.destroy()`，destroy 不会触发 close，所以无重入。OK。

我们来更详细地分析竞态。

场景：用户在某个 tab 中进行了编辑，导致 tabDirty 从 false 变为 true。useTabDirtyAggregate 返回值变化，React 调度 effect。effect 运行后调用 `void window.api.system.setQuitDirty({ dirty: true })`。这是一个异步 IPC 消息发送。在消息到达 main 并被 handler 处理之前，如果用户点击关闭按钮，close 事件在 main 侧触发，`getQuitDirty()` 返回 false（因为 handler 还没执行），于是放行窗口关闭，未保存数据丢失。

这个窗口有多小？用户编辑后，React 状态更新 → 渲染 → effect 运行 → IPC 发送 → 网络/进程间通信 → main 处理。这是一个异步流程，通常在毫秒级。用户要在这个窗口期内点击关闭，概率极低，但确实可能，特别是如果系统很忙或 IPC 延迟。另外，如果用户使用快捷键（如 Ctrl+W）关闭，可能在编辑后立即触发。这确实是正确性缺陷。

但也许项目方已经考虑过，并认为 push 模式足够。简报没有提到这个竞态，只说"规避 close 事件内再等 renderer 应答的时序复杂度"。这暗示他们知道时序问题，但认为 push 模式可以避免反向询问的复杂度。然而，push 模式引入了新的竞态。

有没有更好的方案？一个常见的模式是：在 close 事件中，同步地检查渲染器状态？如果要同步，Electron 的 IPC 是异步的，无法同步。可以通过 `webContents.sendSync` 实现同步 IPC，但通常不推荐，且会阻塞。另一个方案是：在渲染器中，使用 `window.onbeforeunload` 来阻止关闭？但 beforeunload 在渲染器中被触发时，如果返回非 undefined，会阻止关闭？Electron 中，window.onbeforeunload 可以用于拦截，但它不是与 main 通信的好方式。也许可以在渲染器加载时，将初始 dirty 状态缓存，并在每次变化时发送，然后 main 侧维护一个"最近更新"时间戳？但无法知道是否已发送。

实际上，Electron 提供了一种方式：在关闭前，主进程可以询问渲染器，但这是异步的，需要阻止默认关闭，等待渲染器响应。这正是头注禁止的"反向拉取 renderer"，因为它复杂且容易引入死锁。但 push 模式的竞态可以通过确保渲染器在任何可能导致 dirty 的操作后立即发送（即使 dirty 不变）来减轻，但效果有限。

考虑到这是一个本地单用户应用，丢失数据是严重的。但竞态窗口极小，如果用户正常操作，可能不会触发。然而，作为审计，我们应该指出这个缺陷，并建议更稳妥的方案。比如：

我们再看是否有其他竞态：在 close 事件中，如果用户关闭窗口时，IPC handler 正在处理 setQuitDirty，可能 close 事件先到或后到。由于主进程是单线程，事件队列顺序取决于哪个先进入。IPC 消息由渲染进程发送，经过 IPC 通道到达主进程的消息队列。close 事件由操作系统生成，也进入主进程事件循环。两者的顺序无法保证。因此竞态确实存在。

但要触发这个竞态，需要用户在同一瞬间完成 dirty 变化并关闭窗口。实际上，dirty 变化后，React 需要重新渲染、运行 effect、发送 IPC。用户随后关闭窗口，这个过程中有大量时间（至少几毫秒到几十毫秒）。在人类用户的操作中，这是不可能的。用户不可能在同一毫秒内点击两个不同的 UI（比如先点击编辑器按键，再点击关闭按钮）。除非使用键盘快捷键，比如输入文本后立即按 Ctrl+W。但输入文本后，dirty 变化是异步的，但 effect 会在下一次渲染后触发。如果用户在文本输入后非常快地按 Ctrl+W，可能 effect 还没运行。这个窗口期是 React 调度的时间，可能几十毫秒。所以虽然概率低，但理论存在。
