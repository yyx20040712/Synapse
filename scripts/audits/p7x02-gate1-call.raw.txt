## 二、阻断/高优发现

### B-1 【确定-高】 `replayOnStart` 对 send 挂起**无超时保护**：UI 可永久白屏，且「31s 上界」声明仅在 send 最终 settle 时才成立

- 证据（`reading-time-outbox.ts` dispatch 段）：
```ts
try {
  void Promise.resolve(deps.send(...)).then(
    () => finish(true),
    (err: unknown) => finish(false, err)
  )
} catch (err) {
  finish(false, err)
}
```
- `send` 返回的 Promise 若永不 settle（main 侧 IPC handler 繁忙/死锁/排队），条目永远 `in-flight`，`active` 恒 >0。
- 证据（`reading-time-outbox.ts` replay 循环）：
```ts
while (!disposed) {
  pump()
  if (active > 0 || (retryAt !== null && undeterminedOld(maxSeq))) {
    await new Promise<void>((r) => { waiters.push(r) })
    continue
  }
  break
}
```
- `active > 0` 无任何超时分支 → `replayPromise` 永不 resolve。
- 证据（`src/renderer/main.tsx`）：
```ts
await getReaderOutbox().replayOnStart()
createRoot(rootEl).render(...)
```
- **后果**：单条 IPC 挂起 ⇒ 整个应用白屏，无 WARN、无降级路径。票面自裁「31s 上界」只覆盖「send 快速 reject→T4 退避→attempts 拦停」路径；send 挂起时 attempts 永不递增，T6 死信拦停完全不触发。
- 主控预裁以「本地 IPC 即败即还现实面 F3 同族」接受。门一不推翻，但记录为**无代码防护的真实残余风险**——建议至少在 async 入口处加一条 `Promise.race` 超时（如 35s）降级为「跳过存量重放+WARN+继续渲染」。

### A-2 【确定-中】 空 store 启动时「闸门」实质不覆盖任何 enqueue 窗口；窗口保证依赖 UI 未渲染的隐式前提

- 证据（`reading-time-outbox.ts` replay 段）：
```ts
let maxSeq = Number.NEGATIVE_INFINITY
for (const e of mirror.values()) { ... }
gateMaxSeq = maxSeq
```
- 空 store 时 `maxSeq = -Infinity`。`replayOnStart` 同步进入 async IIFE，`pump()` 无条目 → `active = 0`、`retryAt = null` → **立即 break** → `gateMaxSeq = null`。
- 后果：若在 `replayOnStart` 被调用后、promise resolve 前（同步窗口内）有 enqueue，该条目会直接走 `pump()` 派发（因为 gate 已解除）。
- 当前代码路径下 UI 在 await 前不渲染，无实际 enqueue 来源，因此该缺陷**不可触发**。但该保证是「main.tsx 顺序编排」的隐式结果，而非 outbox 自身的闸门语义——测试 `'replayOnStart 幂等：空 store 立即 resolve'` 固化了此行为，却未断言「空 store + 同步窗口 enqueue → 不派发」。若未来有其他装配面在异步窗口内调用 enqueue，闸门承诺破裂。

## 三、边界缺陷

### B-2 【确定-中】 共享退避窗的实际暂停范围 = 全局所有 paper；自裁①只申报了「共享计时器最简读法」，但未申报「暂停所有 paper 的派发」这一额外语义

- 证据（`reading-time-outbox.ts` pump 开头）：
```ts
if (retryAt !== null && deps.now() < retryAt) return
```
- 证据（`reading-time-outbox.ts` onFail）：
```ts
if (!disposed) armBackoff(e.attempts)
```
- 任意 paper 的一次失败 ⇒ `retryAt` 全局置位 ⇒ **所有 paper**（含从未失败者）的队头在退避窗内不派发。
- 测试 `'T4 共享退避闸门：任一失败后退避窗内新条目不派发'` 精确固化了这一全局暂停，并断言 p-b 新条目被 p-a 的失败阻挡。该断言本身**不是设计书要求的**——设计 CO-2 说「跨 paper 并行；共享退避计时器（无 per-entry 独立 timer）」。共享计时器可以只作用于失败条目的重试调度，而**不暂停其他 paper 的首派发**（不涉及越序）。
- 门一判断：实现选择了「全局闸门」这一更简单的可测语义，与 CO-2 的字面冲突已在自裁中部分申报（共享计时器），但**未明确申报「同一退避窗内未失败 paper 的新条目也被暂停派发」**。后果：某 paper 持续失败（最多 5 次/条）会让其他 paper 的时长落库延迟最多 ~31s（退避序列 1+2+4+8+16），在开多 tab 阅读场景下用户关闭的 tab 时长可能延迟落库半分钟。不阻断，但建议补入疑虑清单。

### B-3 【确定-中】 启动期 WARN toast 可能在 App 渲染前发出而丢失（若 toast 挂载点在 App 子树内）

- 证据（`reading-time-setup.ts`）：
```ts
const store: OutboxStore = createLocalStorageOutboxStore(window.localStorage, {
  onCorrupt: (message) => { showToast(message, 'error') }
})
...
outboxSingleton = createReadingTimeOutbox({ ..., onWarn: (message, kind) => { showToast(message, kind) } })
```
- 证据（`src/renderer/main.tsx`）：
```ts
await getReaderOutbox().replayOnStart()   // ← 此期间产生的所有 onWarn/onCorrupt 先于 render
createRoot(rootEl).render(...)
```
- 触发路径：
  1. `getReaderOutbox()` 中 `store.loadAll()` 发现损坏条目 → `onCorrupt` toast；
  2. outbox 构造中 `loadAll` 再触发一次（若损坏未清完）；
  3. `replayOnStart()` 中 T5 恢复后 attempts≥N → `toDeadLetter` → error toast；
  4. `enforceDeadCap()` 淘汰超限死信 → info toast；
  5. store 操作抛错 → `degrade()` → error toast。
- 以上全部发生在 `createRoot(rootEl).render` 之前。若 toast-store 的挂载/渲染由 App 子树驱动，这些 WARN 全部丢失——**死信+WARN 的兜底承诺（设计 §7.2「死信+WARN 不静默丢」）在启动恢复路径上静默失效**。因无法从材料确认 toast-store 挂载结构，标记为确定（触发逻辑存在）但后果取决于挂载点；若 toast 挂在 root 之外的独立 store+portal，则无此问题。**需门二验证 `src/renderer/shared/ui/toast-store.tsx` 的挂载位置**。

### B-4 【确定-低】 退避中的 pending 条目跨重启不继承退避剩余时间；且 T5 的 attempts 拦停不适用于「退避中 pending」状态

- 证据（`reading-time-outbox.ts` replay 段）：
```ts
for (const e of mirror.values()) {
  ...
  if (e.state === 'in-flight') {   // 仅 in-flight 触发 T5 attempts++
    e.attempts += 1
    ...
  }
}
```
- 若条目在 store 中为 `pending` + `attempts=1` + `lastError='db busy'`（上次 T4 reject 后退避中、随后进程退出），重启后：
  - 不满足 `state === 'in-flight'` → 不触发 T5 attempts++；
  - `retryAt = null`（内存态丢失）→ `pump()` 立即派发。
- 后果：退避计时器不跨重启，等效「每次重启清零退避剩余时间」；且每次重启后的首次重试失败前不计 attempts。若进程每 10s 崩溃重启一次，同一 pending 条目可被无限次「重启即重试」，退避形同虚设。由于该状态下 DB 尚未提交（T4 reject 保证），不额外放大 at-least-once 重复加计界，但**失败风暴频次不受 N 上限约束**。设计 §3 T5 表只覆盖 in-flight 驻留，未定义退避中 pending 的恢复语义——实现忠实于字面但未申报此间隙。

### B-5 【确定-低】 dispose 后若 in-flight 回调以 reject 结束，条目被放回 pending 但该会话内不再重试；若随后进程优雅退出，残留条目以 pending 态驻留 store

- 证据（`reading-time-outbox.ts` onFail）：
```ts
} else {
  e.state = 'pending'
  storeUpdate(e)
  if (!disposed) armBackoff(e.attempts)   // disposed=true 时跳过
}
```
- 证据（`reading-time-outbox.ts` dispose）：
```ts
disposed = true
if (timer !== null) deps.timers.clearTimeout(timer)
retryAt = null
```
- 后果：条目留在 store 中 state=pending、attempts 已 +1。下次启动按普通 pending 派发（不触发 T5），不会再有 attempts 累加——与 B-4 同族。属设计未定义的边缘路径（dispose 后进程仍存活的场景），建议在疑虑清单登记。

## 四、页码重放安全（CR-1/CR-3 闭环）审查

### C-1 【不确定-重大】 R7「页码旁路消除」的成立依赖 `scroll-progress.ts` dispose 内部与 `takePending` 共享同一状态池；本包无证据

- 证据（`reading-time-setup.ts` spView）：
```ts
const spView = useMemo(() => {
  const view = {
    ...sp,
    dispose(): void {
      for (const pid of sp.pendingIds()) {
        const page = sp.takePending(pid)
        if (page !== undefined) enqueueReaderProgress(pid, page, 0)
      }
      sp.dispose()
    }
  }
  return view as T
}, [sp])
```
- 代码注释声明「先经 pendingIds/takePending 排干再调原 dispose（其内部直发落库面随排干恒空转）」。**「恒空转」是一个断言，不是已证事实**——它要求 `scroll-progress` 的 `dispose` 内部唯一数据源就是 `pendingIds()/takePending()` 可见的那个容器，且不存在第二条直发路径（如独立 lastReadPage 缓存、或 dispose 内部调用未走 takePending 的发送）。
- 本 diff 未触碰 `scroll-progress.ts`（在档基线 155 文件之一，无 diff），材料中亦无其源码。若 scroll-progress 的 dispose 直接从自身内部状态读 page 而不感知外部 takePending 的排干，则 `sp.dispose()` 仍会直发 `api.reader.saveProgress`——**R7 并入（CR-3）未完整兑现，页码两来源回退窗仍部分存在**。
- **需要门二验证项**：读取 `scroll-progress.ts` 的 `dispose`/`tick`/`save` 实现，确认其所有落库均先经 `takePending` 移除、排干后 dispose 零副作用。

### C-2 【确定-中】 spView 使用对象 spread `{ ...sp }`——若 ScrollProgress 实例方法依赖 `this`，包装视图会破坏方法绑定

- 证据同上：`const view = { ...sp, dispose() {...} }`。
- `ProgressAccountView` 的消费面（`pendingIds/takePending/dispose`）若是闭包对象方法（arrow/闭包捕获）则 spread 安全；若是原型方法 + `this.state` 则 `view.pendingIds()` 调用会因 this 错位而抛错或空转。
- 从测试桩 `makeSpView` 看是闭包形态，但工厂返回形态未在本包中锚定。若真实实现为闭包，风险为零；**需门二读取 `src/renderer/features/reader/scroll-progress.ts` 的 `createReaderScrollProgress` 返回形态确认**。

## 六、报告诚实性对账

### E-1【确定】 自裁⑦「e2e 注种形态」陈述属实，但需注意 e2e **从未端到端验证真实 enqueue 链**

- `reading-time-replay.spec.ts` 全部通过 `w1.evaluate` 直接写 localStorage 注种，注释也声明「真实 enqueue 链由单测全锚」。探针 `p7x02-impl-e2e-probe.mjs` 同型注种。
- 由此，「链路探针两轮 PASS」实际验证的是：**store 载入→T5 恢复→send 链→真实 IPC→真实 sqlite**，而**不是**：阅读计时→收尾口 enqueue→LS 持久化→崩溃→重放。
- 该残余风险已被自裁⑦诚实申报，主控预裁接受。门一复核后确认：申报范围与代码事实一致，无隐瞒。

### E-2【不确定】 verify 文件数 156 vs 基线 155 + 新增 2 测试文件 = 157 的出入

- diff 中新增 `reading-time-outbox.test.ts` 与 `reading-time-replay.spec.ts`；若 verify 的「文件数」含 e2e spec 则应为 157，不含则为 155+1=156（e2e spec 不在 vitest 范围）。报告称 156，存在计数口径不透明的可能。非实质问题，但报告契约要求精确基线——此出入未在自裁中解释。

### E-3【确定-低】 启动期多通道 WARN 的「诚实性」边界

- `reading-time-outbox-store.ts` 的 `loadAll` 损坏自清会调用 `onCorrupt` → toast；而 outbox 内部构造后又调一次 `loadAll`。第一次 loadAll 清掉损坏条目，第二次不会重复触发 onCorrupt——**同一损坏条目只告警一次**，实现正确。
- 但若「第一次 loadAll 成功、第二次 loadAll 抛错」（store 在两次调用之间进入不可用态），第一次的 onCorrupt toast 已在 render 前发出（B-3），随后 outbox degrade 的强 WARN toast 也在 render 前——两条 WARN 均先于 UI 存在。

## 八、结论汇总

- **不阻断**：全部主体票面/设计书条款已落地，态空间 T1~T6 逐格可实现性在单测中锚定。
- **最需门二源码验证的两个不确定项**：
