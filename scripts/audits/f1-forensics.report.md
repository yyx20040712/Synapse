# F1 划选修正役·取证报告（2026-08-29 主控直做——LOOP v2 §2F1「票面前必做」）

> 对象：复测站 3「划选全面失败+选中延迟 0.5~5s 原因不明」。
> 方法：代码级三因子分析 + 真机三号机（playwright `_electron.launch`，真实用户库
> 副本=8 篇真实 PDF，SYNAPSE_USER_DATA 指向临时目录，零触碰真实数据本体）+
> 无阈值像素差分（主控视觉通道不可用环境——Read/子代理 Read 均只回 CDN URL，
> analyze_image 对 CDN 签名 URL 400；以 PowerShell System.Drawing 采样替代，
> 对「可见性」问题反而更客观：着色面积/色值/位置可量化）。
> 产物：`f1-forensics.json`/`f1-forensics2.json`/`f1-forensics3[b].json` + T2/T3 截图。

## 1. 结论（先答用户两问）

1. **「选中延迟 0.5~5s」的真身**：拖选全程**零视觉反馈**（原生 ::selection 被
   F-07 置 transparent，唯一视觉通道=自绘层，而自绘层要等 mouseup 或 200ms
   防抖静止后才渲染）——用户拖多久就「没反应」多久；0.5~5s≈拖选时长本身，
   **不是计算耗时**（取证期零 longtask，evaluate 链 <20ms）。
2. **「全面失败」的真身**：松手后自绘层确实渲染，但 `--accent #2c5f8a` 30%
   alpha 在白纸上的合成色 ≈ rgb(191,207,220)——**约 10% 灰蓝洗，近乎不可见**
   （词选态/基线态像素差分均值 rgb(216,222,223)，段落态 rgb(164,180,191)，
   含文字像素压暗）。叠加碎片化几何（4 字词选=1 窄条+2 零宽伪影；段落选
   =16 行条+零宽伪影），用户观感=「划了没反应/越改越乱」。

## 2. 证据链

### 2.1 密度与分因子（f1-forensics.json——一号机）

- 素材：文献库首卡（真实学术 PDF），可见页 18/19/20 = 396/420/277 span，
  ~12k 字符/页；窗口 2036×1070 CSS（dpr 1.25）。
- **交接假说证伪**：TreeWalker 全遍历中位 **0ms**、双 probe.toString **0ms**、
  40% 页幅 range getClientRects（1061 块）**0.6ms**——`selectionToAnchor`
  的 O(n) 在真实密度下**不构成延迟因子**。
- 程序化选选→自绘层入 DOM（防抖路径）：单词中位 **203ms**、跨行 **218ms**
  ——≈200ms 防抖窗+<20ms evaluate+React commit。
- 一号机「大段超时」=**脚本跨页误选**（span 列表跨三页，被应用跨页拒绝逻辑
  正确静默拦下）——非应用缺陷；二号机页内大段复测正常出层。
- 一号机「真实拖选失败」=**脚本坐标选到视口外**（0.55/0.62 分位在折叠线下
  方）——非应用缺陷；二号机修正后三策略全部工作。

### 2.2 拖选行为（f1-forensics2.json——二号机，全状态转储）

- 策略 A 普通 CDP 拖选 / B 双击选词 / C 慢拖：**全部产生原生选区**
  （selLen 1103/7/1103），拖选静止 600ms 内自绘层+工具条均在 DOM
  （rectsEl=toolbarEl=true）——mouseup 路径与防抖路径机制均工作。
- 页内大段（10%~90% span，9926 字符）：出层，dump 一致。
- 全程 longtask=0；window.onerror/unhandledrejection=0；控制台无错误。

### 2.3 视觉可见性（f1-forensics3/3b.json + 像素差分——三号机）

- 几何转储：词选（4 字符）= rect{x:1232.3,y:775.9,w:**10.2**,h:8.8} +
  **w:0 碎片×2**（其一在层底 y=863 h=21.6——endOfContent 域）；段落选
  （1077 字符）= 16 行条（w≈220~250，h=8.8，行距 8px，隔行 x 交替
  1004.5/1016.5）+ w:0 伪影×1。计算样式 bg=`color(srgb 0.173 0.373 0.541 /
  0.3)`（=--accent 30%，解析正常）。
- **四态蓝/黄像素占比相同**（词选 1.365% ≈ 全页选 1.376%，黄=UI 金饰）→
  蓝黄皆静态 UI 贡献；且 #2c5f8a 30% 的合成色 B-G 差仅 13——常规蓝色阈值
  测不出。
- **无阈值差分**（选区态 vs Escape 基线态，全屏逐 2px，ΔRGB>18）：
  - word：2470 采样点差分，bbox=(1536,916)-(1878,980)（含工具条），均值
    rgb(216,222,223)；
  - para：11948 点，bbox=(1252,676)-(1594,890)（16 行条+工具条），均值
    rgb(164,180,191)。
  - 即：**自绘层在画，但对比度低到实用不可见**；工具条是唯一显著视觉信号。

## 3. 技术路线变迁链复盘（官方→F-06→F-07，用户点名）

| 轮 | 机制 | 用户反馈 | 定性 |
| --- | --- | --- | --- |
| 官方默认 | ::selection rgba(0,0,255,.25) 半透明 | 「不均匀」从未被报 | 基线：零延迟、反馈强、全球 pdf.js/Firefox 同款 |
| F-06 | ::selection 不透明近似色 | **遮字**（P1 复测推翻） | 机制病：不透明+canvas 字形在下=盖字 |
| F-07 | ::selection 透明+自绘层 | **拖选全程无反馈+松手后近乎不可见**（本役复测全面失败） | 机制病×2：视觉通道挂到 mouseup/防抖后=拖选期死寂；30% accent=不可见 |

三轮共同规律：**三次翻车全是机制病（视觉通道选择错误），不是效果病**——
「不均匀」（官方路线唯一已知缺陷）三轮中零次被用户点名。

## 4. 路线裁决依据（详见 ADR-0019）

- **R1（回退官方半透明+删自绘层）**：拖选第一帧即有原生反馈（浏览器内建，
  零代码链路）；rgba(0,0,255,.25) 白纸合成 rgb(191,191,255)，B-R=64——
  本役像素管线原阈值即可测（对比 30% accent 的 B-R=29/B-G=13）；代价=
  重叠 span 叠绘不均匀（轻微、历史上零投诉）。
- R2（优化自绘层：immediate 评估/分流防抖/缓存）保「完美均匀」，但视觉
  通道仍挂在 JS 链路上——三轮已证此路脆弱（L7 延迟预算将永远需要防守）。
- 主控裁决：**R1**。简单机制优于完美效果；F-06/F-07 两轮 [locked-change]
  守卫再次改写（第三次，先例在档）。
