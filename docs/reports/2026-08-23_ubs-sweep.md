## A. 状态维度（store 状态机审计）

### A1 settings.store —— INV-03 缺口属实，并发面【可达（跨通道乱序），低概率高隐蔽】→ 批三修

核实（src/renderer/features/settings/settings.store.ts:43-65）：
- load/save/diagnose 三面均无请求序号守卫（全仓库唯一无 stale-guard 的含异步 load store）。
- 消费方唯一（SettingsPage，grep 全库确认）：
  - load 仅挂载触发（useEffect [load]，load 引用恒稳）——load×load 单实例不可达；
    save×save 由页面 `if (saving) return` 挡（SettingsPage.tsx:61）；diagnose×diagnose
    由本地 diagnosing 态挡（:76）。
  - **load×save 交叉面真实存在**：战役 §5 的 FIFO 假设只对「同步处理器」成立（notes
    get/save）；settings.get 是**异步**处理器（await readFile + 首跑 atomicWrite 回写，
    ipc/settings.ts:45-70），ipcMain.handle 对异步处理器**不保证跨通道回复有序**。时序：
    挂载即发 load（慢）→ 用户秒改邮箱点保存 → save（tmp+rename，快）先回 → S1 落地 →
    load 的旧快照 S0 后到 → `set({ settings: S0 })`（settings.store.ts:45）覆盖 S1 →
    页面 [settings] effect 把表单回同步成旧值（SettingsPage.tsx:53-58）。磁盘数据无损，
    但表单态被旧快照污染 + 用户所见与所存不符。
- 判可达：结构性可达（无序跨通道），概率低（窗口=毫秒级 fs 读），影响中（表单态污染）。
- 动作（批三）：saveSeq 版本计数守卫（load 发起时快照，落地前比对；save 派发与成功
  两点都抬计数）+ 锁定用例（先红后绿）。纯 loadSeq 不够——跨的是不同操作不是两次 load。
- 优先级：P2。

### A3 useAsync —— 无令牌属实，多 run 消费方唯一（PaperDetailPanel），缺陷实锤 → 批四裁决【建议修】

核实（src/renderer/shared/hooks/useAsync.ts:46-60）：
- run() 无请求令牌：仅 mountedRef 防卸载泄漏。旧 run 的 resolve/reject 一律落地。
- 消费方影响面（grep 全库）：LibraryPage（:40，单 run，仅用 run 不用 data/error）、
  FilterBar（:41 collections 静态参考数据，挂载单 run）——两处无令牌需求。
  **PaperDetailPanel（:74-82）唯一多 run 消费方**（paperId/reloadKey 变化重取）。
- 缺陷序列（无需乱序，FIFO 即可触发）：切文献 A→B，A 的 detail 失败、B 成功：
  run#2 起跑 setError(null) → R1(A 失败) 晚于 run#2 起跑到达 → error=msg_A 且
  loading=false（错：run#2 仍在飞）→ R2(B 成功) → data=B、error **残留 msg_A** →
  面板渲染新鲜 B 数据 + "详情刷新失败，显示的是旧数据"红条（PaperDetailPanel.tsx:153-169）
  ——提示语义与实际状态互斥。可达性：A fetch 失败（NOT_FOUND 等）+ 切换即入。
- 动作（批四）：裁决文档 + 建议修——run() 加 runSeq 令牌（await 后比对，data/error
  两路径都守），useAsync.test.tsx 补锁定用例（先红后绿真红面：hook 现无令牌，新用例
  直接红）。单 run 消费方零影响（令牌恒命中）。
- 优先级：P2。

### A4 NotesPanel 保存指示 —— 误显"已保存"窗口【可达】→ 批三修（态空间先行）

核实（src/renderer/features/notes/NotesPanel.tsx:67-81 + notes.store.ts:106-202）：
- 误显场景一（合并落地窗口）：面板挂载期间 load 失败→用户编辑（首载门控挂起保存，
  notes.store.ts:172）→重试成功→合并落地（savedAt=服务器值 T0，saving=false）→
  面板 effect 分支二（:76-79）savedAt 前进→清 unsaved/saveFailed→**显示"已保存"**，
  但草稿含未落库编辑（pendingEdit 在），补存要等防抖 1.5s+保存时长——窗口内
  "已保存"是假话（服务器没有这批编辑）；补存失败会自愈为"保存失败"（分支一）。
- 误显场景二（防抖窗口内切走切回）：saveSoon 已排程未派发时切走→切回（remount）→
  runLoad 立即发 load→合并落地同上；且 remount 把本地 unsaved 复位为 false——
  窗口同场景一。
- 内容安全由 store 不变量保障（pendingEdit 字段级合并，U2 锁定），纯指示失真；
  风险兑现条件=窗口内进程终止（用户看到"已保存"却丢编辑）。
- 根因：面板无法区分"savedAt 因保存成功推进"与"savedAt 因合并落地被赋服务器值"
  ——两因同走分支二。分支二清 unsaved 只在合并场景错、在整版落地场景无意义
  （无 pendingEdit 时 unsaved 本就 false）。
- 动作（批三）：先出态空间表（saving × savedAt × pendingEdit × 面板本地三态的跨格
  序列），修复候选：①分支二不再清 unsaved（保存周期结束分支一已正确收口）；
  ②remount 失真需 store 暴露 pending 语义（NoteDraft 加字段=契约扩展，锁定测试断言
  为逐字段 toBe 非整对象，加字段不破坏既有断言——已核 tests/unit/renderer/notes.store.test.ts）。
  跨格序列（合并落地→补存失败→再 load 等）按宪法交 deepseek 审。
- 优先级：P3（显示层失真，自愈，内容安全）——但任务书明文可达即修。

## D. 复杂度热点（批四裁决预研，本批只取证）

### D1 notes.store 五结构坍缩评估 —— 倾向「不动」，批四落 ADR

  成本=再锁+再审+契约注释重写。红线权衡（任务书 D1）成立性高。ADR 落批四。
- A4 若走 NoteDraft 加 pending 字段，与 D1 裁决互动（加字段≠坍缩，不冲突）。
